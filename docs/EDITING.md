# 编辑功能的可行性评估（暂不实现）

当前 openmd 是只读阅读器。用户要求在所有显示功能完成后再评估“编辑修改文件”的可能性，因此本文只做技术判断，不包含实现。

## 结论摘要

| 格式 | 编辑可行性 | 推荐策略 |
| --- | --- | --- |
| Markdown | 高 | 源码编辑器 + 保留原始文本；富文本所见即所得可作为第二阶段 |
| JSON | 高 | 树节点值编辑 + 保存时重新序列化；保留注释需额外处理 |
| CSV / TSV | 高 | 单元格编辑 + 重新写 CSV；注意引号、换行和编码 |
| TXT / 日志 | 高 | 普通文本编辑器；日志一般不建议原地修改 |
| XLSX | 中高 | 修改目标工作表的 XML；保留公式、样式和共享字符串；或引入成熟库 |
| DOCX | 中 | 修改 `word/document.xml`；图片、编号、关系、样式需要完整 round-trip |
| PDF | 低（内容编辑）/ 中（批注、表单） | 用 PDFium/MuPDF 做批注、表单、页面操作；正文重排不建议 |
| DOC（Word 97） | 低 | 二进制格式复杂；建议只读或转 DOCX 后再编辑 |
| XLS（Excel 97） | 低 | BIFF8 写入风险高；建议转 XLSX 后再编辑 |

## 分格式说明

### Markdown

- 最直接：在源码视图上接入一个多行编辑器（Win32 `EDIT`/RichEdit，或自绘编辑控件），保存时原样写回 UTF-8。
- 现有解析器可以直接用来重新渲染预览；需要增加“未保存修改”状态、撤销/重做、查找替换。
- 难点不在解析，而在编辑体验：光标、选区、滚动同步、输入法、双向文本、表格单元格编辑。
- 如果要所见即所得，建议先做“源码 + 实时预览”，而不是直接实现 Word 式编辑器。

### JSON

- 现有 `JNode` 树可以支持节点值的就地编辑、添加/删除成员、数组元素。
- 保存时用 `PrettyJson()` 序列化即可。
- `.jsonc` / `.json5` 若保留注释和尾逗号，需要额外保存注释 token 和原始布局；否则会丢失格式。
- 大文件编辑需要增量解析或限制节点数量。

### CSV / TSV

- 现有 `GridSheet` 适合单元格编辑。保存时按原分隔符和引号规则写回。
- 需要处理：字段内换行、双引号转义、编码、BOM、超宽表。
- Excel 导出的 CSV 经常带 `sep=,`、千分位等约定，写回时要保持兼容。

### DOCX

技术路线：

1. 把 DOCX 当 ZIP 打开，保留所有未修改的 part；
2. 只修改 `word/document.xml` 中对应的段落/表格文本；
3. 需要保持 `w:rsid`、样式引用、编号、书签、关系 ID 等不变；
4. 保存时重新打包 ZIP。

风险点：

- 复杂字段、内容控件、批注、修订、目录、嵌入对象；
- 图片和超链接的关系 ID 不能重新编号；
- Word 对 XML 顺序和命名空间非常敏感；
- 需要完整 round-trip 测试，不能只用 openmd 自己打开验证。

可参考 [Open XML SDK](https://github.com/dotnet/Open-XML-SDK) 的 part/relationship 模型，但它是 .NET；C++ 侧需要自己实现或引入轻量 OOXML 库。

### XLSX

- 修改 `xl/worksheets/sheetN.xml` 的 `c/v` 内容通常可行。
- 共享字符串（`sharedStrings.xml`）需要同步更新；也可以把修改的单元格改成 `inlineStr`，避免影响其他单元格。
- 公式单元格要区分“公式”和“缓存值”。保存后 Excel 会重新计算，但 openmd 不应伪造计算结果。
- 样式、合并单元格、数据验证、条件格式、图表等 part 必须原样保留。
- 如果要做完整表格编辑，建议先限定“只编辑值、不改公式和样式”。

### PDF

- **正文编辑**非常困难：PDF 是页面描述语言，没有段落/表格语义；文本重排、字体子集、编码映射、坐标变换都很复杂。
- **可行且风险较低**：
  - 高亮、下划线、便签、自由文本等批注；
  - 表单字段填写；
  - 页面旋转、删除、重排、合并；
  - 导出带批注的副本。
- 推荐使用 PDFium 的 `fpdf_annot.h` / `fpdf_formfill.h`，或 MuPDF 的 annotation API；保存时写回新文件，不改原文件。
- 不建议用 PDFium 做“像 Word 一样编辑正文”。

### DOC / XLS（旧二进制）

- Word 97 的 FIB、片段表、PAPX/CHPX、表格流和 OLE 结构非常复杂；写入需要维护所有偏移、FAT 链和校验。
- BIFF8 写入同样需要维护 SST、cell table、XF、FORMAT、CONTINUE 等记录。
- 工程上更合理的是：只读解析 + “另存为 DOCX/XLSX”（需要写 OOXML）或调用系统 Office/LibreOffice 转换；不直接在旧格式上原地编辑。

## 推荐的编辑路线（如果以后要做）

1. **第一阶段：文本类格式**
   - Markdown 源码编辑 + 预览；
   - JSON 树编辑；
   - CSV 单元格编辑；
   - 统一“未保存/撤销/另存为”模型。
2. **第二阶段：Office 值编辑**
   - XLSX 只改单元格值，保留样式/公式/关系；
   - DOCX 只改段落文本，保留样式/图片/关系；
   - 所有保存都写新文件，默认不覆盖原文件。
3. **第三阶段：PDF 批注**
   - 高亮/便签/表单填写；
   - 导出副本，不修改原 PDF。
4. **暂不做**
   - PDF 正文重排；
   - DOC/XLS 原地写入；
   - Word 式所见即所得排版编辑器。

## 对现有架构的影响

- `Document` 需要增加 `dirty`、`undoStack`、`saveAs` 等状态；
- `DocView` 需要从“只读绘制”扩展为“可聚焦的编辑控件”，处理光标、选区、输入法、剪贴板；
- 文件写入必须走“临时文件 + 原子替换”，避免写坏原文件；
- PDF/Office 需要保留原始字节和未修改 part，不能只保留渲染后的文档模型；
- 需要为每种格式建立 round-trip 测试样本。

当前版本不会写入任何被打开的文件；以上内容仅作为后续实现的技术评估。
