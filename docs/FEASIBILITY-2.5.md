## 0. 结论

| 能力 | 可行性 | 工作量 | 风险 | 建议 |
|---|---|---:|---|---|
| 阅读区背景图片 | 高 | 约 900–1,300 行 | 低到中 | 优先做，独立版本 |
| 文本编辑 MVP（独立编辑模式） | 高 | 约 1,000–1,800 行 | 中 | 第二阶段做 |
| 集成源码编辑器（E1） | 中高 | 约 3,000–5,000 行 | 中高 | MVP 验证后再做 |
| 实时预览（E2） | 中高 | 约 800–1,500 行 | 中高 | E1 稳定后做 |
| 预览区直接编辑（E3） | 低到中 | 6,000 行以上 | 高 | 暂不做 |
| 完整所见即所得（E4） | 低 | 很大 | 很高 | 不做 |
| DOCX / XLSX 值编辑 | 中 | 很大 | 高 | 单独评估，不并入 2.5 |
| PDF 正文编辑 | 低 | 很大 | 很高 | 不做；只做批注 |

一句话判断：

- **背景图片是低风险的外观功能，可以直接排进 2.4.2.x。**
- **编辑文件不是“打开一个开关”，而是新增编辑器子系统；应先做最小可用版本，不要直接做 Typora 式编辑。**

## 1. 设置背景图片

### 1.1 当前渲染结构

现状对背景图片是有利的：

- `DocView::Paint()` 每次绘制先 `Canvas::Begin()`，默认用主题背景色清屏，然后才绘制内容。
- `Canvas::Image()` 已经支持本地路径或内存图片，内部使用 WIC 解码、Direct2D 绘制，并有 1 亿像素上限。
- 设置窗口是自绘的滚动页面，增加一个“背景图片”区块不需要重做窗口框架。
- 导出走独立的 `Canvas` 和 `PaintContent(..., exportOnly=true)`，可以明确控制背景是否进入导出。

需要处理的地方：

- 正文没有“纸张”层，文字直接画在主题背景上；如果背景图片直接铺满，文字对比度会下降。
- `PaintGrid()` 会整屏填充主题背景，`PaintSource()` 也有侧栏底色，背景需要按模式选择是否透出。
- PDF 页面本身是白底，图片模式也有自己的底色；背景只应出现在页面外的留白区域。
- 导出默认不应包含用户背景，否则“阅读背景”会意外进入 PNG/PDF。

### 1.2 推荐产品形态

不要做“全窗口无差别铺图”。推荐三层：

```text
背景图片
  -> 半透明遮罩（scrim）
  -> 阅读纸张层（可选，默认开启）
  -> 正文 / 列表 / 卡片
```

提供两种模式：

| 模式 | 效果 | 适用 |
|---|---|---|
| 边缘背景（默认） | 正文下方有半透明纸张，背景主要显示在左右留白 | 长时间阅读，保证对比度 |
| 沉浸背景 | 背景铺满阅读区，只加遮罩，不加纸张 | 欢迎页、演示、短文档 |

默认参数建议：

- 填充方式：`cover`（等比铺满，居中裁切）
- 遮罩：35%
- 纸张不透明度：88%
- 背景不透明度：100%
- 虚化：第一版不做
- 作用范围：欢迎页、Markdown/文本正文、PDF/图片的页面外留白
- 不作用：工具栏、标签栏、工作区侧栏、源码/JSON/表格模式

源码、JSON、表格模式保持不透明，因为这些是“工作界面”，背景会干扰阅读和后续编辑。

> 2.4.2.0 实际实现采用更轻量的方案：不强制增加大面积纸张层；背景不透明度为 5%–60%，默认 15%；同时提供填充方式和 3×3 裁剪位置。详见 `docs/BACKGROUND-IMAGE.md`。

### 1.3 设置项

在 `Settings` 中增加：

```cpp
bool backgroundEnabled = false;
std::wstring backgroundPath;
int backgroundFit = 0;        // 0 cover, 1 contain, 2 tile
int backgroundOpacity = 100;  // 20-100
int backgroundScrim = 35;     // 0-70
int backgroundPaper = 88;     // 0-100, 0 = 沉浸模式
bool backgroundInExport = false;
```

路径处理：

- 只接受本地文件，不允许 `http://` / `https://`。
- 支持 WIC 能解码的格式：PNG、JPEG、BMP、GIF、TIFF、WEBP、ICO。
- 配置保存绝对路径；文件丢失时回退主题背景，并在设置页显示“文件不存在”。
- 可选增强：提供“复制到配置目录”，避免用户移动原图后失效。第一版可以不做。

设置界面：

```text
设置
└─ 外观
   └─ 背景图片
      [选择图片] [清除]
      预览缩略图
      填充方式：铺满 / 完整显示 / 平铺
      背景不透明度：滑块
      遮罩强度：滑块
      纸张不透明度：滑块
      在导出中包含背景：复选框
```

建议放在现有“外观”区块下面，或做成独立的小窗口。后者更干净，但多一些窗口代码。

### 1.4 渲染实现

新增一个轻量模块：

```text
src/background_image.h/.cpp
  BackgroundImage
    Load(path, error)
    Ready()
    Source()        // 下采样后的 WIC 位图源
    CacheKey()
```

绘制顺序：

```cpp
Canvas::Begin(hwnd, palette, /*clear=*/false);
PaintBackground(c);     // 填充主题底色 + 图片 + 遮罩
PaintContent(c);        // 原有内容
Canvas::End();
```

`PaintBackground` 的逻辑：

```text
1. 先用 palette.bg 填满，保证图片失败时仍有正常背景。
2. 没有启用或加载失败：直接返回。
3. 计算 cover/contain 目标矩形。
4. DrawBitmap(bitmap, dest, opacity)。
5. 叠加遮罩色（深色主题用黑，浅色主题用白/深灰）。
6. 正文模式再画纸张矩形。
```

关键点：

- **不要每帧解码**。按“路径 + 修改时间 + 文件大小”缓存，设置变化或文件变化时重载。
- **不要每帧新建位图**。每个 `DocView` 的 `Canvas` 已经按 `cacheKey` 缓存 D2D 位图。
- **解码前限制尺寸**。继续使用 1 亿像素上限，但背景建议更严格：文件不超过 64 MB，像素不超过 6,000 万；超过时拒绝并提示。
- **下采样**。背景只需要显示到窗口尺寸，建议在 WIC 侧缩放到视口 2 倍以内再创建 D2D 位图，避免 8K 图片占用几百 MB。
- **多标签内存**。每个标签页有自己的 `Canvas`，同一张背景会在每个标签各创建一份 D2D 位图。可以在标签隐藏时释放位图，或只让活动标签持有背景位图；第一版先限制像素，通常可以接受。
- **DPI 变化**。`Canvas::Begin()` 在 DPI 变化时会重建渲染目标；背景位图缓存需要一起失效。
- **导出**。`PaintContent(exportOnly=true)` 默认不调用 `PaintBackground`；只有用户勾选“导出包含背景”才绘制。

各模式行为：

| 模式 | 背景 | 说明 |
|---|---|---|
| Welcome | 显示 | 加遮罩，保持文字和最近记录可读 |
| Document | 显示 | 默认加纸张层；沉浸模式只加遮罩 |
| Source | 不显示 | 保持纯色工作区 |
| Json | 不显示 | 保持纯色工作区 |
| Grid | 不显示 | 表格需要稳定对比度 |
| Pdf | 页面外显示 | PDF 页面仍是白底，背景只在页间和两侧 |
| Image | 页面外显示 | 图片本身不变，背景只在四周 |
| Error | 显示或纯色 | 建议纯色，避免错误信息被背景干扰 |

### 1.5 风险与规避

| 风险 | 规避 |
|---|---|
| 文字对比度不足 | 默认纸张 88%；遮罩下限 25%；提供对比度提示 |
| 大图解码卡顿 | 限制 64 MB / 6,000 万像素；下采样；首次加载可显示“正在加载背景” |
| 多标签内存翻倍 | 限制像素；非活动标签释放位图；共享 WIC 源 |
| 图片丢失 | 回退主题背景，设置页提示，不阻塞打开文档 |
| 导出被污染 | 默认不导出；显式选项 |
| 主题切换后不协调 | 遮罩颜色跟随明暗主题；纸张颜色使用当前主题的 `bg/surface` |
| 透明 PNG | WIC 转 32bppPBGRA，保留透明；下方先铺主题色 |

### 1.6 验收标准

- 选择一张 4K JPEG 后，欢迎页和 Markdown 正文显示背景，文字仍清晰。
- 切换主题、缩放、调整窗口大小后背景不拉伸变形。
- 删除背景文件后重新打开，程序正常显示主题背景并提示文件不存在。
- 打开多个标签不会因为同一张背景导致明显内存增长或卡顿。
- 导出 PNG/PDF 默认不包含背景；勾选后才包含。
- 源码、JSON、表格、PDF 页面本身不受背景影响。

### 1.7 工作量

| 部分 | 预计 |
|---|---:|
| 设置字段与读写 | 50–80 行 |
| 背景加载/下采样/缓存 | 300–450 行 |
| 渲染与纸张层 | 150–250 行 |
| 各视图接入 | 150–250 行 |
| 设置界面 | 250–350 行 |
| 国际化与提示 | 30–50 行 |
| **合计** | **约 900–1,300 行** |

复杂度低到中，适合一个独立版本。

## 2. 编辑文件

### 2.1 当前代码事实

必须先明确：当前项目没有任何文本编辑能力。

- `DocView` 的源码模式是自绘只读视图；`Handle()` 没有 `WM_CHAR`、`WM_IME_*`、光标或插入符处理。
- `WM_KEYDOWN` 只处理画笔选择、删除、方向键移动等少量局部按键。
- `BuildSource()` 把 `doc_->text` 切成行，超过 200,000 行会截断显示。
- `doc_->text` 在加载时已经做了换行归一化，原始 CRLF/LF 没有保存在 `Document` 中。
- `Document` 保存了编码枚举和编码名，但没有保存 BOM、原始换行风格、原始文件时间/大小。
- `DecodeText()` 会剥离 BOM；目前没有公开的“按原编码写回”函数，只有 `EncodingCodePage()` 可用。
- `Ctrl+S` 当前绑定的是“保存笔记”（`CMD_SAVE_NOTES`），不是保存文档。
- 文字高亮按 `block + start + length` 保存；正文一旦重排，块索引和偏移会漂移。
- 文件监听会在外部修改时自动重载；自己保存后必须抑制这次重载。
- `WriteFileBytes()` 直接 `CREATE_ALWAYS` 覆盖，不适合作为文档保存；笔记保存已经使用了“临时文件 + `MoveFileEx`”的原子替换模式，可以复用。

因此，编辑功能至少需要新增：

```text
文本缓冲区
光标 / 选区 / 输入法
撤销 / 重做
保存编码与换行
脏标记与关闭提示
外部修改冲突处理
标签页和快捷键集成
```

这不是在现有源码视图上加一个 `WM_CHAR` 就能完成的。

### 2.2 可编辑范围

建议第一版只做“有原始文本的文件”：

| 格式 | 第一版 | 说明 |
|---|---|---|
| `.md` / `.markdown` | 可编辑 | 主要目标 |
| `.txt` / 日志 / 代码 / 配置 | 可编辑 | 纯文本 |
| `.json` | 可编辑源码 | 不保证保留注释和原始缩进 |
| `.csv` / `.tsv` | 可编辑源码 | 表格单元格编辑另做 |
| `.xml` / `.yaml` / `.ini` | 可编辑源码 | 纯文本 |
| `.ipynb` | 暂只读 | JSON 结构复杂，错误保存会破坏 notebook |
| PDF / 图片 | 只读 | 不做正文编辑 |
| DOCX / XLSX | 只读 | 需要 OOXML round-trip，风险高 |
| DOC / XLS | 只读 | 旧二进制格式，不建议写入 |

二进制黑名单和 512 MB 上限继续保留。编辑还应增加更小的实际上限，例如 32 MB 或 200,000 行，超过后提示“仅阅读”。

### 2.3 方案 A：最小编辑模式（推荐先做）

不直接改造自绘源码视图，而是增加一个“编辑”模式：

```text
DocView 只读预览
  -> 点击“编辑”或 Ctrl+E
  -> 打开独立编辑窗口/覆盖层
  -> 载入 doc_->text
  -> 保存后重新加载预览
```

编辑器实现有两种选择：

#### A1：RichEdit（最快）

使用系统 `Msftedit.dll` 的 `RICHEDIT50W` 控件：

- 原生光标、选区、输入法、剪贴板、撤销/重做；
- 支持大文本；
- 通过 `EM_SETBKGNDCOLOR`、`WM_SETFONT` 适配主题和字号；
- 单 exe 仍然成立，`Msftedit.dll` 是 Windows 系统组件，不是额外运行时。

代价：

- 外观与当前自绘源码视图不一致；
- 没有行号和语法高亮；
- 缩放、边距、主题需要额外适配；
- 需要处理 RichEdit 的自动链接、拖放等默认行为。

预计 1,000–1,800 行，适合作为 MVP。

#### A2：自绘最小编辑器

复用当前源码视图的排版，增加：

- 光标与选区；
- 鼠标点击/拖选/双击选词；
- `WM_CHAR` 和 `WM_IME_*`；
- 剪贴板、撤销/重做；
- 光标滚动跟随。

外观更统一，但工作量明显更大，接近方案 B 的核心部分。

### 2.4 方案 B：集成源码编辑器（E1）

如果 MVP 验证后要继续，建议新增独立模块：

```text
src/editor_buffer.h/.cpp
  - 文本缓冲区（gap buffer 或 piece table）
  - 行索引
  - 插入/删除/替换
  - 撤销/重做
  - 脏区间

src/source_editor.h/.cpp
  - 光标、选区、输入法
  - 鼠标命中测试
  - 键盘与剪贴板
  - 滚动跟随
```

接入方式：

```text
DocView::Mode::Source
  -> 只读时使用现有 PaintSource
  -> 编辑时切换到 SourceEditor
  -> 保存成功后重建 doc_->text 和预览
```

保存管线：

```text
Ctrl+S
  -> 检查只读/文件占用
  -> 比较磁盘文件时间与大小
  -> 编码为原始编码
  -> 写入同目录临时文件
  -> MoveFileEx(REPLACE_EXISTING | WRITE_THROUGH)
  -> 更新文件时间
  -> 清除脏标记
  -> 抑制一次文件监听事件
```

需要新增的文本元数据：

```cpp
enum class LineEnding { Lf, CrLf, Cr };

struct TextFileMeta {
    TextEncoding encoding = TextEncoding::Auto;
    UINT codePage = CP_UTF8;
    bool bom = false;
    LineEnding eol = LineEnding::Lf;
    uint64_t fileTime = 0;
    uint64_t fileSize = 0;
};
```

保存规则：

- UTF-8：按原 BOM 决定是否写 BOM。
- UTF-16/UTF-32：按原字节序和 BOM 写回。
- GBK/Big5/Shift-JIS 等：按原代码页编码；遇到无法表示的字符时提示“改用 UTF-8 另存”。
- 原始换行风格保留；新输入行沿用同一风格。
- 如果加载时做过乱码修复（`encodingRepaired`），默认不允许原地覆盖，建议“另存为 UTF-8”，避免把修复后的文本写回原编码。
- 只读文件、被占用、网络盘写入失败都要明确提示，不能静默失败。

### 2.5 标签页与关闭提示

需要增加文档级脏状态：

```cpp
bool dirty = false;
uint64_t editRevision = 0;
```

行为：

- 标签标题显示未保存标记，例如 `● README.md`。
- 关闭标签、切换文档、退出程序时提示“保存 / 不保存 / 取消”。
- 保存失败时保持标签打开和脏状态。
- 外部修改时提示“重新加载 / 保留当前编辑 / 另存为”。
- 自己保存后忽略一次 watcher 事件，避免刚保存就重载。

快捷键冲突：

- 当前 `Ctrl+S` 是保存笔记。
- 建议改为：`Ctrl+S` 保存文档；`Ctrl+Alt+S` 保存笔记；笔记工具栏按钮保持不变。
- 如果用户没有编辑，`Ctrl+S` 可以继续保存笔记，保持兼容。
- `Ctrl+Shift+S` 另存为。

### 2.6 注释与编辑的冲突

这是编辑功能最容易被忽略的部分。

- 文字高亮保存的是 `block`、`start`、`length`；正文修改后，块索引和字符偏移都可能变化。
- 画笔和图形标注按页面坐标保存，正文变长后位置也会漂移。
- 笔记文件按文档路径哈希保存，编辑正文不会覆盖笔记文件，但笔记可能对不上内容。

第一版建议采用保守策略：

```text
文档有笔记/高亮时：
  - 允许编辑，但保存前提示“注释可能错位”
  - 或者禁止编辑，要求先导出/清除注释
```

更好的长期方案是给高亮增加“所在段落文本哈希 + 偏移”，保存后按内容重新锚定；但这会增加复杂度，不应放进第一版。

### 2.7 实时预览（E2）

现有分屏视图可以复用：左侧源码编辑，右侧预览。

实现要点：

- 输入后 250–400 ms 防抖，避免每次按键都全量解析。
- 解析放到后台线程；新编辑使旧解析任务失效。
- 解析完成后回到 UI 线程替换预览，保留滚动位置。
- 超过阈值（例如 2 MB 或 50,000 行）暂停实时预览，改为手动“刷新预览”。
- 编辑期间画笔模式禁用，避免焦点冲突。

预计 800–1,500 行。依赖 E1 的稳定缓冲区和保存模型。

### 2.8 工作量

| 方案 | 内容 | 预计 |
|---|---|---:|
| A1 | RichEdit MVP：编辑、保存、脏标记、编码保留 | 1,000–1,800 行 |
| A2 | 自绘最小编辑器 | 1,800–3,000 行 |
| B | 集成源码编辑器 E1 | 3,000–5,000 行 |
| E2 | 实时预览、冲突处理、滚动同步 | +800–1,500 行 |
| E3 | 预览区直接编辑 | 6,000 行以上，不建议 |

### 2.9 验收标准

- 打开 UTF-8 Markdown，修改后 `Ctrl+S`，文件内容正确，编码和换行不变。
- 打开 UTF-8 BOM / UTF-16 LE / GBK 文件，保存后 BOM 和编码保持。
- 只读文件保存失败时给出明确提示，不丢失编辑内容。
- 外部修改后保存时检测冲突，提供覆盖/重新加载/另存为。
- 关闭未保存标签时提示，取消后标签仍在。
- 保存后文件监听不会立即触发重载。
- 有文字高亮时给出注释可能错位的提示。
- 超过编辑上限的文件自动只读。
- 保存过程使用临时文件 + 原子替换，写入失败不破坏原文件。

---

## 3. 推荐实施顺序

### 2.4.2.x：背景图片

先做背景图片，原因：

- 不改动文档加载、解析、保存和标签生命周期；
- 可以独立验收；
- 视觉收益明显；
- 风险主要集中在解码内存和对比度，容易控制。

### 2.4.3.x：文本编辑 MVP

只做：

- `.md` / `.txt` / `.json` / `.csv` 源码编辑；
- RichEdit 或等价的最小编辑器；
- `Ctrl+S` 保存、另存为、脏标记、关闭提示；
- 原编码/BOM/换行保留；
- 原子写入和外部冲突提示。

暂不做：

- 实时预览；
- 行号、语法高亮；
- 注释重锚定；
- Office/PDF 编辑。

### 2.5.0：集成编辑器与实时预览

只有在 MVP 被实际使用后再投入：

- 自绘源码编辑器；
- 分屏实时预览；
- 更完整的撤销/重做和查找替换；
- 注释锚定策略。

### 暂不纳入

- PDF 正文编辑；
- DOCX/XLSX 原地 round-trip；
- DOC/XLS 写入；
- Typora 式所见即所得；
- 预览区直接改 Markdown。

---

## 4. 最终建议

1. **背景图片可以做，而且应该先做。** 它的实现边界清晰，不需要改动编辑和文档模型。
2. **编辑文件可以做，但先做最小版本。** 当前源码视图完全只读，直接做完整编辑器会把一个外观版本变成大型子系统。
3. **不要同时做背景、编辑、实时预览和注释重锚定。** 这四项叠加会显著增加回归风险。
4. **编辑功能应排在异步文档打开之后，或至少限制可编辑文件大小。** 否则大文件保存和预览仍会卡住 UI。

推荐的版本节奏：

```text
2.4.2.0  背景图片
2.4.3.0  异步文档打开（PROJECT-SOLUTIONS 的 P0）
2.5.0.0  文本编辑 MVP
2.5.1.0  实时预览与冲突处理
```

如果希望更快看到编辑能力，也可以把编辑 MVP 提前到 2.4.3.0，但必须限制文件大小，并接受首版没有实时预览。
